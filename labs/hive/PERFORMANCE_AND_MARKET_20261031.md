# HIVE — high-precision Qwythos and decentralized compute performance gate

**Evidence date:** 2026-10-31. **Scope:** source and tests executed in an ephemeral ChatGPT Linux CPU sandbox. No user machines, ChatGPT fleet, public volunteers, external GPU, rented provider, or Qwythos weight files were used.

## Real execution environment

Observed with `lscpu`, `free -h`, `df -h`, `nvidia-smi` availability, and PyTorch 2.10.0+cpu:
- Intel Xeon Platinum 8573C, 5 visible vCPU, 5.8 GiB RAM (~4.7 GiB available at the time), ~30 GiB disk free;
- no CUDA device, no NVIDIA driver tools, and no access to other virtual machine instances;
- Hugging Face OAuth account was free (not PRO); Hugging Face Jobs were empty. **No billed jobs were started.**

Qwythos 9B v2 model weights cannot fit here at Q5, Q6, Q8 or BF16 without an unacceptable partial/offload strategy. This repository **does not implement Qwythos's Gated-DeltaNet or recurrent/KV state propagation**. `qwythos_plan.py` is an illustrative contiguous-range planner only, not a working Qwythos sharding engine. Do not imply the toy transformer is the Qwythos model.

## Reproducible local measurements

Using 4-layer randomly initialized toy decoder, 32-dimensional hidden state, two independent HTTP worker *processes on the same physical host*, 4 generated byte-tokens, alternating order, warmup before 5 requests per path. Full raw timings in `hive-real-loopback-receipt.json` and `hive-synthetic-latency-receipt.json`, supplied separately with the package.

| Route | Monolith median | Distributed median | Slowdown | Exact generated tokens |
|---|---:|---:|---:|---|
| 2-worker loopback | 1.913 ms | 14.724 ms | 7.699x | yes |
| 2-worker loopback plus **synthetic** 15 ms delay per forward | 2.086 ms | 134.984 ms | 64.700x | yes |

Synthetic delay means software `sleep` injected in-process, **not observed WAN RTT**. The loopback trial is actual cross-process HTTP but has no real WAN, separate GPU or Qwythos. The small sample and tiny model cannot extrapolate to Qwythos performance. It does establish a measured regression from naïve sharding.

Reproduce with:

```sh
cd labs/hive
python -m unittest discover -s tests -v
python -m hive.local_benchmark --samples 5 --delay-ms 0 --output /tmp/hive-loopback.json
python -m hive.local_benchmark --samples 5 --delay-ms 15 --output /tmp/hive-delay.json
```

## Mechanism for protecting end-user performance

`hive/performance_gate.py`: candidate admission is **fail closed**, requiring exact same model ID, weights digest, precision, task/workload ID, execution environment, recent trusted runtime measurements, correct output, budget, and sufficient samples. It rejects higher p95, first-token p95 or median latency. Unqualified and stale results keep local mode. It is a **decision gate**, not a runtime hard-SLA guarantee: changes in load or host failure require continuous measurement and failover, and the `VERIFIED_RUNTIME` provenance needs independent attestation rather than self-declaration.

`hive/placement_guard.py`: only *proposes* single-device Qwythos Q5/Q6/Q8/BF16 admission from observed peak VRAM (not weight size), worker consent, model digest verification, compatible hybrid engine, budget and hardware evidence. Free-only `$0` by default. It cannot run inference or reserve resources.

**A higher-precision target must not be compared to Q4 as if outputs or quality were identical.** Compare Q8 vs Q8 or BF16 vs BF16 under the same workload for pure performance. Compare Q8 vs Q4 on independent quality, latency, energy and cost axes, acknowledging the tradeoff.

### Architecture choices

1. **Use one suitably sized GPU first** for Q8/BF16 (single 24 GiB GPU *may* fit BF16 short contexts; verify runtime peak). This avoids WAN per-token communications. A local Q6 attempt on 8 GiB is plausible but may lack context/buffer headroom.
2. **Geographically separate workers:** best for independent prompts, evaluator jobs, LoRA/adapter tasks, and asynchronous RL rollouts; network only exchanges requests/results/checkpoints, not each token's per-layer activations. This permits high hardware utilization without claiming identical latency.
3. **WAN layer sharding:** when per-token network costs are dominated by model compute or hidden via validated speculation/pipelining and layer locality; requires Qwen3.5 Gated-DeltaNet engine support, sequence state correctness, adversarial worker validation, transport authentication, performance receipts, and remote model weight access. A generic toy transformer is not sufficient.
4. **Distributed training:** prioritize asynchronous rollout/evaluation or well-understood elastic training; gradient all-reduce across residential WAN can be catastrophic without specialized algorithms.

## Practical next operator-approved hardware test

1. On existing Slink, without disrupting other GPU jobs, inspect installed model weights and current compute owner. No service restart, download, spending, or irreversible changes by default.
2. Acquire/verify Qwythos-v2 Q6 / Q8 / BF16 weights from the official Hugging Face repository under its license; record revisions, SHA256, model metadata, and download size. Q8/BF16 on a single **adequately provisioned** GPU is the first high-quality baseline.
3. Use pinned llama.cpp on a trusted private GPU with the Qwen3.5 hybrid implementation and record context, output, true VRAM peak, warm TTFT, decode tok/s, power, energy, and task-quality metrics (including quality comparison vs Q4).
4. Compare same-precision monolithic vs multi-host on real authorized peers with the same prompts/context, warmups, repeated measurements, p95 and throughput. First target separate LAN machines. Avoid public llama.cpp RPC endpoints; its backend is an insecure PoC per https://github.com/ggml-org/llama.cpp/tree/master/tools/rpc .
5. Only enable WAN sharding if correctness and p95/median/TTFT qualify. Otherwise route high-precision requests to a single adequately provisioned provider GPU and independent tasks to the swarm.
