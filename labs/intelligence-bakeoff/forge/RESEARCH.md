# Research program and source record

## What is implemented

The first capability slice uses three project-authored, source-attributed Markdown cards and SQLite FTS5/BM25. A deterministic policy analyzer and separate evidence reconciliation cover a narrow synthetic Conditional Access subset. The native plugin was loaded into a temporary Hermes profile and exercised through real Hermes dispatch and a terminal result hook with no model or network calls. The included caller-invoked route handles a narrow single-policy synthetic question and refuses mutation requests, but is not wired into a user's live conversation.

A first CPU-only comparison used a locally available Qwythos 9B v2 MTP Q4 GGUF and four synthetic policies fixed before the run. The model and deterministic tool each produced all four expected verdicts; the tool reconciled all four evidence records. Across those four calls, the model path took 22,915.6 ms and direct Hermes tool dispatch took 34.7 ms, approximately 661× for that sum. Both paths used the same synthetic policy facts on the same host; the model received explicit decision rules. This is a comparison of **a direct model call with an already-selected deterministic tool**, not a 661× faster model or end-to-end autonomous agent. It excludes model-server startup and the decision about whether to call the tool. Four cases cannot establish general parity or no regressions.

The CPU-only child was bound to an owned loopback port and stopped after the run. The actual model file SHA-256 matched the publisher's checksum. The private receipt records the exact prompt protocol, source commit, runner and plugin file hashes, model hash, llama.cpp version, per-case timings and verdicts. A follow-up suite of five newly specified unsupported and ambiguous cases returned 5/5 expected tool verdicts and 3/5 model verdicts under the explicitly conservative rubric. The model took 40,434.2 ms in total and selected tool dispatch took 34.3 ms. These are exploratory results, not claims about every real Entra policy.

A nine-case confirmation repeated the previously observed cases with one common conservative prompt and timed the route decision, Hermes dispatch and evidence verification. On the hardened implementation, Qwythos matched 7/9 specified verdicts and the route matched 9/9 with 9/9 evidence checks; total times were 79,929.4 ms and 57.1 ms respectively, approximately 1,401× for this sum. The fixed cases had already been seen in the earlier pilots, so this is a repeatability check, not a new independent holdout. It includes a caller-supplied fixture and policy ID, but not natural-language entity extraction, production integration, model-server startup or plugin startup. The model received the policy facts and explicit decision rules; the verifier shares the same synthetic input and is not an independent Microsoft implementation. This does not establish general agent speed or quality parity. The owned CPU-only server was stopped after the run. Network access was configured for loopback but was not instrumented in this benchmark.

The index/result cache also has a smaller, separate performance effect. In one local nine-sample, 1,500-query-per-sample FTS5 microbenchmark on the three current cards, the median fell from 195.7 to 51.9 microseconds per query, with exact result equality on the benchmark queries. This 3.8× result is limited to warm local retrieval; it is not an end-to-end speedup. Corpus contents are hashed on each lookup, so a same-size change with a restored modification time invalidates the cache. Thread isolation and returned-object mutation are regression-tested.

## Qwythos adapter feasibility

The publisher's [Qwythos-9B-v2 checkpoint](https://huggingface.co/empero-ai/Qwythos-9B-v2/tree/2178f73a9b5ea28ccd8f6096ef6bac5cd59c9d8b) advertises Apache-2.0, 9,653,104,368 BF16 parameters, `Qwen3_5ForConditionalGeneration`, a 32-layer hybrid text stack and a vision stack. The matching [GGUF release](https://huggingface.co/empero-ai/Qwythos-9B-v2-GGUF/tree/97c11b03687f194b300efbdb4760d9bc4021b759) is a separate quantized deployment artifact. The checkpoint's own `chat_template.jinja` and tensor header were retrieved by bounded metadata/range requests; weights were not downloaded for this audit. The installed GGUF was already present and separately hashed for the CPU comparison.

A possible **tool-use reliability** pilot is rank-8 LoRA on the 16 `q_proj`/`v_proj` modules in the eight full-attention layers, freezing the vision stack and other weights. The published tensor header exposes those names and shapes; the rank-8 A/B matrices total 1,114,112 parameters before optimizer or metadata overhead. [Transformers' Qwen3.5 implementation](https://github.com/huggingface/transformers/blob/66f51e76efd8542232b8bdd40ade7d1edbaac46f/src/transformers/models/qwen3_5/modeling_qwen3_5.py) and [PEFT's LoRA configuration](https://huggingface.co/docs/peft/en/package_reference/lora) provide architecture and targeting evidence. The inspected [PEFT target mapping](https://github.com/huggingface/peft/blob/03412afcf1e96f74a014e467a313b22baeb74498/src/peft/utils/constants.py) does not contain an automatic `qwen3_5` entry; enumerate real `named_modules()` and specify an explicit validated target pattern. This is a plausible experiment, not a demonstrated compatible training run.

BF16 weights alone are roughly 18 GiB before activations and optimizer state; a 4-bit theoretical weight floor does not establish fit. QLoRA compute, mixed precision, activation memory and CPU offload need an actual isolated fit probe. [llama.cpp's LoRA converter](https://github.com/ggml-org/llama.cpp/blob/0138937e3f987f70e90e97d022c73ecb9bec037c/convert_lora_to_gguf.py) is a separate conversion and serving path; a reported [Qwen3.5 adapter conversion failure](https://github.com/ggml-org/llama.cpp/issues/21125) makes an exact-version round trip and held-out comparison mandatory. The issue is evidence of a reported failure, not proof that every adapter or current revision fails. An [MLX-LM Qwen3.5 implementation](https://github.com/ml-explore/mlx-lm/blob/736ab0d8c1d0edc79c3d798044fe6904e2fa23be/mlx_lm/models/qwen3_5.py) exists, but MLX conversion and training are untested here.

Before training, require: a substantially larger rights-cleared, privacy-reviewed dataset; leakage-resistant split by session and failure family; a frozen baseline against the actual Qwythos serving artifact; explicit regression limits; a bounded memory probe; loss and checkpoint evidence; unchanged base weights; adapter load/conversion verification; and a real comparison on independent held-out trajectories. Four synthetic training examples are far below that bar. An Entra domain adapter must beat retrieval on held-out, source-versioned tasks before it is justified. A small specialist model must beat the deterministic policy on total task success and resource use, not merely router classification accuracy. No training, fit probe, adapter conversion or promotion has been executed.

## Next experiments

| Hypothesis and mechanism | Minimum comparison and measurement | Falsification or stop condition |
|---|---|---|
| Evidence records reduce unsupported success claims by preserving state and exit code. | Compare the same frozen failures with and without the hook using the same local model, tools, task inputs, budgets and verifier; report claims grounded in observations, task completion, calls and elapsed time. | Reject or revise if unsupported claims do not fall, valid outputs are lost, or tool calls increase materially. |
| Deterministic routing can avoid expensive model calls for a small declared task class. | Expand the single-policy synthetic evaluation with independently specified positive, negative and unsupported cases; then test the actual pre-model route in an isolated Haven/Hermes session, including routing overhead and fallback behavior. | Reject automatic routing if unknown inputs are guessed, evidence fails reconciliation, or held-out outcomes regress. The nine-case confirmation includes the helper routing and evidence checks but excludes entity extraction and production integration. |
| FTS5 retrieval can supply current versioned knowledge more reliably than memorization. | Compare no retrieval and source-attributed retrieval on versioned, license-reviewed, disjoint tasks; score provenance, correctness and stale-source refusal. | Reject retrieval if it increases ungrounded claims or retrieved text changes operational authority. |
| Compact durable task state reduces repeated retries after interruption. | Replay sanitized, verified trajectories with and without goal/evidence/rejected-approach state, then restart at the same boundary. Measure repeated calls and completed tasks. | Reject if useful context is lost or completed work is falsely marked complete. |
| Adaptive reasoning budgets reduce latency without reducing verified outcomes. | Use a fixed held-out mix and identical model/runtime; compare bounded direct, tool and deeper-reasoning policies on success, total tokens and wall time. | Reject if any protected safety/authorization or critical capability regresses, or speed gains disappear after all calls are counted. |
| A specialist model beats a small deterministic classifier. | First benchmark a rules baseline; then compare the specialist using the same tasks, total model calls, latency, memory and regressions. | Defer training if deterministic rules perform as well or the specialist cannot fit without disrupting an owner. |
| Qwythos LoRA improves residual tool use after harness fixes. | Run a small adapter only after data and fit gates; compare base, adapter and an equal-data deterministic/oracle control over disjoint tasks. | Reject if held-out success or security/authorization checks regress, or if gains are explained by control data alone. |

## Candidate external capabilities

The machine-readable [integration inventory](experiments/integration-inventory.json) records GitHub-reported license and last push time as observed on 2026-10-31. A recent push is not a security audit or integration acceptance.

| Candidate | Observed direction and boundary |
|---|---|
| Maester, Microsoft Graph SDKs | MIT metadata; evaluate read-only, scoped assessment adapters when a synthetic-to-real contract and authorization are ready. |
| ROADtools | MIT metadata; research tenant-identity analysis in a separately authorized environment, not by automatic credential collection. |
| Azure MCP | The earlier `Azure/azure-mcp` repository is archived; the active `microsoft/mcp` catalog is the current lead. Verify the exact server, permissions, version and license before installing. |
| Prowler, ScoutSuite | GitHub reports Apache-2.0 and GPL-2.0 respectively. Prefer an isolated CLI adapter with normalized evidence; review compatibility and licensing before redistribution. ScoutSuite's last recorded push was older than the other listed repositories. |
| Sigma, MITRE ATT&CK, osquery, Semgrep | GitHub metadata alone did not resolve every license (`NOASSERTION` for some); review the actual data, rules and code licenses separately. Any scanner needs explicit scope and its own capability grant. |

No external integration in that table is installed, authenticated or run by this package. Source snapshots and SHA-256 values are listed in [compatibility-sources.json](experiments/compatibility-sources.json).
