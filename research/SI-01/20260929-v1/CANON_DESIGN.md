# A durable Haven canon without context drift

PROPOSED design for later H00/operator review. This packet establishes anchor points now; it does not install a generator, rewrite root navigation or declare a new source of higher authority.

## One front door; several maintained records

A single enormous 'super bible' would be readable at first but difficult to update and expensive to load into every agent. Recommend a compact canonical front door with a human-readable full edition generated from maintained records. Generation is an assembly operation with citations, not an opportunity for an LLM to silently reinterpret decisions.

Proposed future modules:

- NORTH_STAR: operator intent, retained V01–V16 anchors, human outcomes, principles and explicit non-goals.
- DECISIONS: versioned decision IDs, status, exact evidence, affected contracts/requirements, owner/reviewer/operator authorization and supersession chain.
- CAPABILITIES: what exists, what was actually executed, independent review, applicable conditions, unresolved failures and next test. These are separate fields, not a single DONE flag.
- ARCHITECTURE_INDEX: the accepted I01–I07 baseline and additive domain adapters by version; do not copy competing schemas into each chapter.
- EVIDENCE_INDEX: source and test receipts, exact artifacts, input/output/fixture identities, negative results, uncertainty and invalidation scope.
- ACTIVE_WORK: each live grant's source, checkout/paths, deadline, budget, true agent/task state and resume point.
- FRONTIERS: ambitious branches retained with a useful re-entry experiment rather than forgotten or mislabeled implemented.

These can remain Markdown plus small JSON records and the existing GitHub workflow. No new database, vector service or always-on memory daemon is necessary for the initial project canon.

## Do not conflate two kinds of memory

Project memory contains public-safe intent, design, tasks, tests and decisions. Personal world memory contains authorized observations, people, places and private events. They may share provenance and correction patterns, but private household maps, biosignals, recordings and personal histories do not belong in this public repository.

The canon should explain the private system's design and evidence using synthetic examples. It should never become an accidental collection point for raw personal data.

## Suggested minimal capability record

Use a logical record with capability ID, purpose, owner, retained anchors, design revision, implementation revision, executed test/protocol/environment, independent review, supported claim class, known failures, applicability/invalidation conditions, source rights and next admissible action. Unknown fields remain explicitly unknown.

Example: 'selected-image answer on artificial fixtures' can have implementation and execution evidence while 'real-world visual grounding', 'metric reconstruction', 'device enrollment' and 'robot motion' remain separate unqualified claims. A passing documentation review does not fill execution fields.

## Compact role-specific context packet

Before dispatch, assemble the mission paragraph; exact active authorization; applicable accepted decisions/contracts; pinned hard-input references; task/output/path constraints; known blockers and superseded instructions; and the next review gate. Use links and content hashes instead of reproducing every research report. Prefer a small navigable packet, with size chosen for the task, over a ritual context-token quota.

The specialist reads the underlying relevant sections and returns an INPUT_USE-style mapping from source finding to its actual implementation or conclusion. Citations identify what was used, not just what files were listed. If a source changes, invalidate affected conclusions and require the bounded recheck; do not restart unrelated domains.

## Conflict and evolution rules

PRECEDENCE.md remains controlling. Current explicit operator scope is distinct from proposals and historical prompts. Newer timestamps alone do not win. Reconcile exact conflicting claims and affected owners, preserve old versions and record the accepted correction. A discovered webpage or unknown issue commenter cannot grant execution.

Before a canon update, show what changed, why, its source, affected original IDs and whether the change is intent, accepted design, implementation, execution or qualification. Reject duplicate IDs, dangling references, missing owners and untraceable supersession as documentary integrity defects. Such checks do not establish scientific truth.

## Context reconstruction acceptance test

A future fresh reviewer should be able to answer, using only the canon and its links:

What are we building? What is explicitly not the final product? What can actually run now? What was tested, on which inputs and revision? What remains speculative? What is the active task allowed to change? Why was a design chosen? What superseded it? Which previous failures remain relevant? What should happen next without expanding authority?

Test this with a fresh native context, not with the original author recalling the answers. Missing evidence should produce a specific gap rather than a confident summary. This is the project's counterpart to a source-grounded personal memory system.
