# Authority, precedence and additive scope

Use separate axes: **what the project ultimately aims to do**, **what is currently authorized to be implemented**, and **what has actually been demonstrated**. None implies the other two.

1. Current explicit user directions and applicable tool/system constraints govern the present task. The latest request makes all follow-ups additive and requests a complete handoff.
2. Current explicit approvals govern implementation. The existing local Codex thread has M0 authority, not blanket permission for this repository's future branches.
3. The operator-approved current M0 plan and review clarifications govern M0. Its source is the visible conversation, reproduced with attribution in the baseline context file.
4. The original Generation-0 implementation plan governs M0–M6 and its R0/S1/S2 gates unless an approved change is recorded. It refines the earlier broad architecture.
5. This cumulative v1.0 design is the current proposed **total scope** and coordination structure. It adds daily, wearables, spatial sensing, emergency networking, robotics and fabrication; it does not silently supersede approved milestone contracts.
6. Archived earlier prompts, pricing and preflight findings are historical context. New public documentation can update a factual finding, but cannot itself authorize changing tested pins or user permissions.

A future follow-up is appended as a requirement with provenance, owner, acceptance path and affected contracts. Never delete a prior branch because the conversation has moved to a newer branch. To defer a capability, preserve its identifier and state the dependency. To remove it, obtain explicit owner approval and retain the rationale.

## State vocabulary

`USER_REQUIREMENT`, `DESIGN_PROPOSAL`, `DOCUMENTED_EXTERNAL`, `METADATA_ONLY`, `UNVERIFIED`, `IN_PROGRESS_REPORTED`, `EXECUTED_PASS`, `EXECUTED_FAIL`, `BLOCKED`, `PENDING_OPERATOR`, `SUPERSEDED_BY_APPROVED_CHANGE`.

An experiment planned in a paper is not an experiment performed by Haven. A vendor demonstration is not clinical certification. A synthetic test passing does not qualify a real device. A model's explanation is not an authorization record.

## Conflict process

Record the two claims, sources/versions, affected requirements, operational consequence and recommended resolution. Propose the smallest change. H00 reconciles design; Eric approves scope/authority; H06 reviews evidence. The author of a runtime capability cannot be its sole acceptance authority. In an unresolved safety or identity conflict, inhibit the affected action but keep unrelated useful tasks available.
