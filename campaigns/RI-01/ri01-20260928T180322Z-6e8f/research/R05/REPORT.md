## Decisions

### D1. Integration summary and useful first slice

Build toward a finite agenda reader: “What is on my selected calendar in the next seven days, and where could I put 30 minutes for the workshop?” A deterministic projection returns exact event times, source links, freshness, conflicts and unknown coverage. A local editable plan can suggest gaps without reserving them. This is useful before an LLM, subscription, background watcher, mailbox ingestion or new hardware exists. Keep a one-shot refresh explicit and stop when its bounded request completes.

Proposed first live provider, only after separate authorization and only if the user already uses it: Google Calendar with `https://www.googleapis.com/auth/calendar.events.owned.readonly`, one resolved owned calendar, seven-day interval and minimal fields. This scope covers owned calendars more broadly than the selected calendar; the broker must enforce a narrower account/calendar/window allowlist. If the user uses Microsoft, select Graph delegated `Calendars.ReadBasic` and calendarView instead; do not make them create a Google account. Shared-calendar access is a separate scope/rights decision. Begin today’s coding proposal with synthetic fixtures, not OAuth. A user-supplied public/synthetic ICS fixture or manually entered plan is the account-free fallback. [S01, S02, S12]

Default proposal bounds: 250 events total, five pages maximum, 30 seconds total read deadline, at most two read retries, no attachments, bodies or attendee lists unless the particular question needs separately permitted fields. Reaching a limit produces “Partial calendar view” with the covered interval and truncation; it does not produce a free-time guarantee. An empty page with a next-page token is not a completed empty result. Availability means no eligible blocking item found in the stated complete projection, not proof the human is free. [S02]

R05 extends CORE I07 with domain-specific proposal and observation types; it does not create another authority service or mutate CORE. It preserves R01 S1 recall, S2 decision/engineering planning, S3 drafts/reminders, S4 selected-image questions and S5 cooperative field/replay work. Calendar/file links can attach to those journeys with lineage. A workshop photograph, speech input, map marker or friendly personality cannot authorize a write. Digital logistics support later physical campaigns; a reminder saying “launch” is never a flight permit.

### D3. Provider and permission comparison

| Domain | Google route | Microsoft route | Design consequence |
|---|---|---|---|
| Calendar reads | Calendar v3 events.list; owned-readonly or broader events.readonly; free/busy scopes for availability-only questions. | Graph v1.0 calendarView; delegated Calendars.ReadBasic for basic detail, higher scope only when required. | Calendar projection needs explicit interval and recurrence expansion; provider output-timezone header cannot repair incorrectly specified query offsets. [S01,S02,S12] |
| Mail reads/drafts/send | gmail.metadata and gmail.readonly are restricted; gmail.send sensitive; gmail.compose restricted and includes send. | Mail.ReadBasic for basic list; body requires appropriate higher permission. Mail.ReadWrite and Mail.Send are distinct permissions. | Local draft needs no mail token. Provider grants are often broader than the exact operation; local allowlists and explicit send approval remain necessary. [S05,S13,S14] |
| Files | drive.file is per app-selected files, non-sensitive, but grants write as well as read. drive.readonly is broad/restricted. | Delegated Files.Read for own file reading; write routes require Files.ReadWrite. | “Selected file” is not automatically provider-enforced read-only. Prefer user-selected imported content or a GET-only broker profile; do not recursively crawl a drive. [S07,S15,S16] |
| Tasks | tasks.readonly versus tasks; task due is a date, API discards time. | Tasks.Read/Tasks.ReadWrite; To Do task has dueDateTime, reminderDateTime, isReminderOn and recurrence. | Google task date cannot implement an exact 08:00 alarm. Graph reminder fields do not prove OS notification delivery. [S09,S10,S17,S18] |
| Native reminders | No assumption that Calendar event reminder equals device delivery. | No assumption that Graph task creation equals notification display. | A qualified native adapter may be better than a hosted service. Apple EventKit permissions are native, including event full/write-only and reminders access; no claim of generic iCloud REST equivalence. [S23; accepted R01] |

OAuth authentication identifies the issuer/account and obtains provider scopes. Haven consent separately binds purpose, exact resource, subject rights, time, output route and digital effect. A visible MCP tool or installed connector conveys neither. Delegated Graph permissions act within both app scopes and the signed-in user’s access; app-only access is a materially different administrator-controlled design, excluded from this first slice. Tenant policies can prevent consent even where a permission normally needs no administrator. [S11]

Native OAuth should use system browser authorization with PKCE and an exact registered redirect; an installed app cannot hold a confidential client secret. Google documents that incremental authorization is not supported for installed apps/devices, so do not blindly apply web-server incremental-consent recipes. Validate actual returned scopes, token issuer/audience/account and state; no model receives tokens. Store refresh credentials only in the qualified broker/OS secret store, never public logs. Expired/revoked tokens stop the operation and request bounded reauthentication; they do not trigger broad scopes or alternate-user credentials. [S04]

Two users enroll independently. AccountBinding includes Haven principal, provider issuer/subject, account/resource namespace, granted scopes, token-secret reference, operation allowlist, account epoch and connector revision. Account relink, logout or switch increments binding epoch and invalidates pending proposals. A’s Google token cannot read B’s Microsoft account by tool-name similarity. UI shows the acting account before every future write. Connecting an employer mailbox requires actual authority/rights, not just technical success.

### D4. Honest operation states and exact write profiles

Separate local intent, durable domain operation and observed external outcome:

- `LOCAL_DRAFT`: local commit, no dispatch allowed. “Saved here; not sent” requires authoritative local-only/no-dispatch proof.
- `APPROVED_PROPOSAL`: authenticated review of exact canonical payload, resource revision, recipients, account, source closure and expiry. No external effect yet.
- `ATTEMPT_ADMITTED`: one domain attempt consumed durably before network work; no network inside the authority transaction.
- `PROVIDER_ACCEPTED`, `PROVIDER_RESOURCE_OBSERVED`, `ATTEMPT_OUTCOME_UNKNOWN`, `REJECTED_BEFORE_DISPATCH`, and `CONFLICT` are different observations. A timeout after admission may mean the provider committed.
- Recipient-client delivery signals, where available, are separate and limited. None establishes a named human read or understood a message. Cancellation/revocation fences future actions without rewriting prior possible disclosure.

These digital-effect records are separate from CORE I06’s four output records: ReleaseAuthorizationReceipt, ConsumptionPermitReceipt, append-only DeliveryObservation, and PermitEligibilityDecision. R03 uses related release/delivery receipt terminology; CORE names are the integration vocabulary. Do not use a UI release permit as permission to create an event or send mail. A digital effect and a subsequent private status message each require their applicable authority. Source lineage applies to subject/recipient/body/attachments and even metadata. [CORE I01/I06/I07; R01 amendment]

An adapter profile must bind API/version/method/route, resource namespace, payload canonicalization, changed-payload conflict rule, provider dedup scope/lifetime evidence, preconditions, successful response meaning and permitted reconciliation endpoints. Until each is qualified, mutation retries are disabled, including SDK middleware retries. Read retry may use bounded backoff/Retry-After, preserving lease expiry and throttling state. [S24]

Lookup results must remain distinct: (a) exact authenticated matching resource, (b) authenticated conflicting resource, (c) successful complete no-current-match, (d) truncated/incomplete search, (e) 401 authentication failure, (f) 403 authorization/quota failure, (g) 404 resource-or-access ambiguity, (h) 429 throttle, (i) 5xx/server error, (j) timeout/network failure. Only (a) supports observed matching commit. Even (c) does not prove a write never committed and was later deleted. Error paths cannot mint another attempt, refund a finite claim or label a message “not sent.” A future operator may authorize a new operation after reviewing unresolved duplicate risk; this is not an automatic retry.

Calendar `sendUpdates=none` is not a universal “no external communication” safeguard; Google documents side effects and warnings. A future private test create should omit attendees and use a separately reviewed no-notification profile. Email sends always disclose to exact To/Cc/Bcc recipients and potentially provider processing; destination-only approval does not declassify source subjects. [S03]

### D5. Durable schedules, recurrence and bounded proactivity

`ScheduleSpec v0-proposed`: schedule_id, immutable revision, owner/account binding, purpose, source closure, wall-time intent or absolute instant, named timezone and tzdb version, recurrence representation/version, start/end/count, explicit DST gap/fold policy, next-occurrence preview, destination/audience/route, quiet-hours policy, catch-up window/max count, expiry, recurring-operation authorization reference, job/lease/cancel epochs, operation budget and created/updated receipt. No raw OAuth token or model-generated grant.

`OccurrenceRecord`: schedule_id/revision, stable intended local occurrence plus fold discriminator or provider original occurrence identity, calculated UTC instant, calculation rules version, state DUE/MISSED/CANCELLED/ADMITTED/OUTCOME_UNKNOWN/OBSERVED, lease owner/fence, domain attempt ID and separate release/consume/delivery refs. Key by intended occurrence, never process boot time or last poll time. Series edits create a new schedule revision with explicit cutover and cancellation of replaced future occurrences. “This one”, “this series” and “this and following” are distinct user choices; do not silently translate them into broad series writes.

RFC5545 distinguishes datetime interpretation from recurrence expansion: ambiguous local datetime selects first occurrence; nonexistent datetime uses the pre-gap offset, whereas generated invalid/nonexistent recurrence instances are ignored and not counted. A human reminder policy may offer skip or explicit shift and fold choice, but that is Haven semantics and must not be mislabeled RFC behavior. Preview next three occurrences and one applicable DST transition. Reject unsupported recurrence conversions rather than approximate Google RRULE into Graph’s pattern/range. Date-only/all-day events remain dates with exclusive end semantics where applicable, not assumed midnight deadlines. Query interval offsets and output timezone are separate. [S12,S25,S26]

Proposed conservative reminder default: one catch-up cue within 20 minutes of the intended time, otherwise mark missed and show it on next authorized foreground review. User selects this explicitly when scheduling. Never catch up an occurrence whose prior effect is unknown. Quiet-hour routine digests may batch, but no conversational preference disables a separately qualified alarm channel. Calendar travel-time/physical readiness is an inference, not guaranteed availability. Device sleep, disabled notifications and missing network are distinct failure causes.

Q-R05-01 clarification is a supervisor interpretation plus this author’s proposal, not a new R03/CORE author agreement: ordinary restart of a provably intact current database may retain schedule and occurrence facts. Every new due publication requires fresh full authority/time/lease checks. Previously consumed permits cannot revive; unknown attempts are reconciled read-only. Backup/import/rollback restore uses a new authority/restore epoch and review-only schedules, with no automatic tokens/timers/attempts. If intact-state versus rollback cannot be established, quarantine. This preserves R03 CONTRACTS F’s explicit restored-backup boundary and clarifies CORE I02’s compressed wording.

Each recurrence is a new release under a separately approved bounded recurring-operation profile: principal, purpose, interval/end/count, per-occurrence payload constraints, destinations, total budget, quiet-hours/catch-up policy and revocation. The current finite R03 P0 claim remains ONE_RELEASE_ONE_DESTINATION_WHOLE_OUTPUT: debit parent quota once when admitting the release, consume the existing claim without debiting again or requiring positive remaining parent quota. For several required finite grants, all charges occur atomically or none do, deduplicating the same grant/profile in the source closure. Grant authorization revision remains distinct from quota accounting sequence, so charging cannot invalidate its own claim. A spent one-use claim never becomes recurring permission. Same key returns history, changed tuple conflicts, and unknown does not refund/remint. Proposed recurrence needs separate review; this report does not grant it.

Finite agenda research ends after its query and report. “Watch for changes”, daily digests, webhooks/push, polling and notification subscription renewal are ongoing work, requiring explicit schedule/monitor scope, stop control, resource ceiling and expiry. Calendar push channels expire and do not renew automatically; channel overlap can happen, so event/source revision dedup and full reconciliation matter. No watcher is created here. [S27]

### D6. Source changes, offline and privacy

Provider event/file/message IDs are provider/account/container-scoped, not interchangeable across services. Graph event default IDs can change on move (ImmutableId is a documented option); Graph iCalUId differs for each recurring occurrence, while Google recurring instances share an iCalUID. Store adapter-specific stable/original-instance identities and source revisions, not just a meeting title or cross-provider UID. [S19,S22]

Capture provider modification/ETag/version, fetch receipt time, source hash/field projection and query coverage. Correction or deletion tombstones old active content and invalidates derived agenda, draft, attachment and queued notification dependencies. Google sync token 410 requires a full re-sync; clear the active projection and mark freshness unavailable until a replacement is complete. This is not permission to delete required minimal historical attempt/receipt evidence or continue exposing stale private data. Preserve historical records only under authorized retention. [S28]

Offline private/shared cached answers and queued content cannot be newly released or replayed without current applicable grant verification. UI: “I can’t verify current sharing permission while offline, so this queued answer is unavailable until I reconnect.” A new independently authored local note can be saved only under its applicable local policy; it is not a derivative declassification trick. Generic notification metadata still needs its audience policy. Formerly exported or shown content may persist and cannot be recalled. Revocation does not erase an unknown remote send. No automatic cloud fallback or source upload when a local path fails.

A summary needs its own sharing grant AND all applicable parent source/subject/rights dependencies. A cannot declassify B/bystander information. Imported file content, calendar descriptions and received mail are untrusted data, never executable instructions or OAuth consent. Source corrections fence pending output even if its visible text did not quote that source. A future independently reviewed release/declassification flow is outside current R03 P0.

## Risks and open questions

The smallest useful live slice depends on the user’s existing provider, exact app registration/consent route, provider terms and separately authorized private data. Those are not needed for the synthetic coding package. Calendar/document metadata itself can be sensitive. Mailbox restricted-scope verification and possible security assessment make broad Gmail ingestion costly compared with selected files/calendar reads. Affordability: account-free fixtures and deterministic agenda/scheduler need no model or subscription; reuse the existing language/runtime after implementation approval. A native provider UI plus manual local draft is a bounded alternative when integration overhead outweighs value. Google Calendar currently documents no additional cost for standard use, with planned charges for quota excess later in 2026; recheck before deployment and never enable billing automatically. Graph/device/vendor costs and tenant entitlements are UNKNOWN for this user. Existing-account costs are not zero-cost claims. Two independently configured accounts double consent/admin work, not necessarily infrastructure. [S29]

Maturity ladder: L0 reviewed research (this handback); L1 synthetic deterministic read/schedule/reconciliation harness; L2 one independently authorized finite live read-only account/window; L3 separately qualified native/synthetic notification with observed delivery limits; L4 endpoint-specific reviewed digital writes; L5 bounded recurring/cooperative workflows across independently enrolled users; L6 multimodal field/engineering logistics coupled to separately qualified physical systems. No level follows automatically from the previous one. R02 inference lifecycle/containment prerequisites noted by VISION-ARCH remain prerequisites before any real model pilot.

Biggest integration risk: a generic retry helper may turn a transport timeout into a second mail/task write, or a “restart” path may import stale authority. Keep endpoint retry policy and rollback detection in the adapter qualification boundary. Unknown outcome is a visible useful state, not an error to hide.
