## Shared identity and authority
RecordRef = type, id, positive revision, content_sha256. IDs are 1–128 ASCII letters/digits/underscore/hyphen; revision is integer 1..2147483647 and never wraps. Hashes are lowercase 64-character SHA256. Hash raw artifacts over exact bytes. I02 requires separate raw and metadata digests; it does not supply an executable canonicalizer. This proposal names R08MetadataV1: UTF-8 JSON with no BOM/whitespace, ASCII object keys sorted lexicographically, arrays in recorded order, booleans/null in JSON spelling, exact bounded integers in shortest decimal form and all measured decimals as strings. Reject duplicate keys, noninteger JSON numbers and unpaired Unicode surrogates; preserve Unicode strings without normalization. Escape quotation mark/backslash, encode every U+0000..001F as lowercase four-digit Unicode escape, leave other Unicode scalar values literal, and do not escape slash. Hash the record object excluding only its top-level content_sha256 field. Nested RecordRef hashes remain included. Schema implementation and independent vectors must confirm these bytes before coding acceptance. Unsupported canonicalization versions reject; records cannot reference mutable latest aliases. Storage IDs are opaque I02 refs, never arbitrary filesystem paths. No path import or URL fetch occurs in this package.

All authority is derived from accepted I01's complete vector, including joint source closure and uncited context; a client-supplied reviewer name does not grant access. In the inert package, two synthetic principals have explicit fixture roles PROPOSER and REVIEWER; authorization through the accepted authority interface is tested. This does not qualify real human identity or grant management. Reviewer-only holdout payload is never passed to proposer/search; deny attempts and their metadata are retained under appropriate access. A second LLM does not establish reviewer competence or independence.

Maximums: two synthetic people, 32 source objects, 16 grants, 128 provenance edges/depth16, 64KiB metadata record and 256KiB whole released output, consistent with CORE-P0. Across one inert run: five candidate revisions, 160 scalar events including corrections/reference rows, 20 proposed test families, one process, 600000ms total wall ceiling, zero model calls/external spend. Exceeding a bound rejects/stops without truncating evidence or silently increasing budget. These are processing/test limits, not physical tolerances or permission for capture.

Bounds apply together;160 events is not permission for160 independent source objects. A frozen synthetic batch may contain multiple scalar rows with exact row locators/digests sharing one raw artifact source. A correction uses a new immutable batch/revision and provenance edge; it never edits the old batch. Stop when any source/edge/depth/byte/event cap is reached. Do not hide distinct sources as rows merely to bypass the authority closure.

## Exact scalar and time rules: Q-CORE-04 closure proposal
Parse numbers from decimal strings into exact integer/rational arithmetic before range checks; reject JSON floating-point values, booleans, exponent notation, whitespace, NaN, infinity and UNKNOWN where a numeric value is required. UNKNOWN is a distinct tagged status with null value/reason. Input syntax is optional minus, a canonical integer part (no leading zeros except zero), optionally a decimal point and one or more digits. Normalize negative zero to zero only in canonical metadata, retaining raw bytes.

Length profile: raw unit mm or m, dimension LENGTH_DISPLACEMENT, declared scale exactly 1/1000 or 1 respectively, offset exactly zero. Raw mm permits at most six decimal places and magnitude <=1000mm; raw m permits at most nine decimal places and magnitude <=1m. Canonical m is a decimal string with exactly nine places and magnitude <=1.000000000m. Scaling is exact; no rounding or clipping. Thus 12.500000mm -> 0.012500000m; 0.000001mm -> 0.000000001m; 0.0000001mm rejects rather than rounding. A raw 1000.000001mm rejects on range. A claimed canonical 12.5m for raw12.5mm rejects. A consistently but falsely labeled sensor value cannot be detected by a unit parser alone; independent acquisition/reference checks are required later.

These +/-1m and precision limits are explicit first-profile storage bounds, not evidence of nanometre instrument accuracy. Nominal precision is carried separately from uncertainty. Missing/ambiguous frame, datum, axis, conversion or raw precision rejects normal ingestion; an opaque original can remain an I02 source without becoming a scalar fact.

Known scalar uncertainty uses the same declared length unit and exact scale, range 0..1m, canonical nine-place decimals; expanded and standard uncertainty remain distinct with method and correlation/contributor refs. Coverage factor is a dimensionless decimal string, >0 and <=10, at most six fractional places, unchanged by unit conversion. Known expanded uncertainty must equal the declared exact standard uncertainty times coverage factor within this profile's representable precision; otherwise reject this profile, not approximate. Zero uncertainty is only an explicitly synthetic mathematical fixture with method SYNTHETIC_EXACT; real zero-error claims are not admitted. UNKNOWN calibration or uncertainty may be represented as tagged null with reason and forces INCONCLUSIVE/ineligible analysis. Never replace UNKNOWN by zero.

Budget-duration input seconds is a nonnegative decimal string, converted by exact multiplication by1000 to integer ms. Permitted range 0..604800000ms (seven days of representable planning duration); fractional ms, overflow, NaN/Inf/UNKNOWN reject numeric budget admission. 0.001s ->1ms; 0.0005s rejects; 604800.001s rejects. A zero duration means no admitted positive work, not infinite time. This outer schema range does not override a smaller authoritative reservation or the inert run's600000ms cap.

clock_uncertainty_ms has tagged KNOWN integer0..604800000 or UNKNOWN/null. Conversion from clock_uncertainty_s obeys the same exactness rule, but uncertainty is never added to a budget or interpreted as an instant. UTC capture/receive strings are validated RFC3339 with explicit Z, retain distinct semantics and cannot stand in for monotonic deadline receipts. Clock epoch must match source metadata; unknown/changed epoch blocks freshness-based eligibility. Parent I04 defines actual monotonic worker deadlines; this no-worker profile does not infer them from wall timestamps.

Translational standard/expanded uncertainty x1e-3; radians, quaternion components and dimensionless coverage factors unchanged. These later validation tolerances are not invented by scalar v1.
